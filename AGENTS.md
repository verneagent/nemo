# Nemo

Lark-connected coding agent daemon. Repo focus:
- Lark/relay-facing orchestration in Python
- coding-agent runtime behind `CodingAgent` (Claude or Codex)
- channel I/O behind `Channel`

## Working Model

- Keep `nemo/agent.py` as orchestration only. Push agent-specific logic into concrete adapters such as `LarkChannel`, `ClaudeCodingAgent`, and `CodexCodingAgent`.
- `agent.py` is channel-agnostic and agent-agnostic. It only sees `Channel` and `CodingAgent` abstractions. Lark-specific logic (file download, message enrichment, API calls) belongs in `LarkChannel`. SDK-specific logic belongs in the concrete `CodingAgent` adapters.
- The coding agent is selected by `--agent claude|codex|opencode` (default `claude`). `nemo/agent_factory.py` maps the agent kind to its adapter and enforces agent/model compatibility. ("Provider" in this repo means a *model* provider — DeepSeek / Kimi / Anthropic — and only appears in `nemo/models.json`'s top-level `providers` grouping.)
- Reasoning effort is a shared `low/medium/high/max` knob (`--effort` at startup, `/effort` at runtime) exposed on `CodingAgent.set_effort`. Each adapter translates: `ClaudeCodingAgent` passes the value through the SDK's native `ClaudeAgentOptions.effort` parameter (claude-agent-sdk ≥ 0.1.50); `CodexCodingAgent` passes `--effort` to the sidecar, which sets `ThreadOptions.modelReasoningEffort` (clamps `max` → `high`, since the Codex SDK has no `max` tier); `OpenCodeCodingAgent` injects a prompt prefix (also clamps `max` → `high`). Because Claude's effort lives on SDK options rather than per-turn input, the host reconnects with `resume=<sdk_session_id>` after `/effort` so the new value takes effect on the next turn — session context is preserved across the reconnect.
- Prefer relay-backed event delivery. Direct Lark 长连接 is only a fallback when relay is not configured.
- Preserve the one-card-per-turn model: turn cards evolve through PATCH instead of emitting a new card for each phase.
- **A steered turn answers two questions — both answers belong in the Done body.** The CLI runs a steered follow-up as its OWN query, so the turn emits a complete answer, then another one. The Done card's body used to be only the LAST answer step, so the reply to the first question was demoted into the collapsible Thinking panel and looked "buried" (2026-10-29, oc_956058b1…). `_note_steer_answer` snapshots the trailing answer step when a steer is accepted (only when it IS an answer — a tool/thinking step means the model had not finished, and promoting narration would be noise) and `_done_body_segments` turns those into `body_segments`, rendered as separate markdown blocks divided by an `hr`. Do NOT use formatting heuristics (e.g. "bold text looks important") to promote content out of the timeline: thinking routinely bold-sections itself, and the structural signal — a steer started a new query — is exact.
- Keep turn execution event-driven. `run_turn()` should emit typed events and the main loop should react to them.
- Stop/esc only interrupts the current turn — do not reset or restart the SDK client. Session and conversation context must be preserved (match CLI Escape behavior).
- **Never query over an unsettled stream.** `claude_agent_sdk`'s `receive_messages()` is ONE single-consumer stream that outlives any turn, so a turn that stops reading while the CLI still owes it a `ResultMessage` strands that Result in the buffer — the next reader claims it as its own answer and every card answers the PREVIOUS message, permanently (+1 turn lag; three incidents: 2026-07-16 steer continuation, 2026-08-20 resumed empty first Result, 2026-09-20 same-client retry). `claude_turn.ResultLedger` (one per `SDKThread` client, NOT per turn) is the single accounting point: `owe()` after every accepted `query()` (including `SDKThread.steer`), `consume()` for every Result read off the stream, and the stream is settled when the two are equal. It replaces the per-incident flags (`steered`/`resumed`/`retry_same_client`) — a same-client retry needs no flag because the previous attempt's obligation is still on the books, so the retry owes two. Three rules protect it: (a) `SDKThread.run_turn_with_reconnect` drains at the turn boundary (`drain_outstanding`, surfacing stragglers as late output) and RECONNECTS if the drain comes up empty — the obligation then dies with the old subprocess instead of leaking forward; (b) the expectation comes from `ledger.begin_attempt()`'s `AttemptBooks` snapshot, never from the counters — they are private (`_owed`/`_consumed`) and cumulative for the client's lifetime, so turn N reading them directly computes an expectation of N and hangs waiting for Results consumed turns ago (a real bug, caught only by re-reading the code); (c) the idle drainer shares the same stream and must count what it takes (`consume_if_owed()`), while `steer()` obligations the transcript probe calls folded are written off (`reconcile_to`) — a folded steer emits ONE Result for TWO queries, and a phantom obligation would make every later boundary reconnect for a straggler that does not exist.
- **The SDK client belongs to the SDK loop.** `receive_messages()` and the rest of the client's async surface are bound to the loop the client was created on; awaiting one from the host loop does NOT raise — it never completes, which looks exactly like a hung CLI (the turn-boundary drain was written that way once). Read the client only through `SDKThread._client_on_sdk_loop()` (raises on the wrong loop) and only from a coroutine scheduled with `run_on_sdk_loop(...)` (or the idle drainer task). `tests/test_sdk_thread.py:test_client_stream_is_only_touched_on_its_own_loop` (AST guard) + `test_client_access_off_the_sdk_loop_raises` (runtime guard) pin both halves.
- The between-turn idle drainer (`SDKThread._idle_drain_loop`) surfaces background-task completions via `set_idle_notifier` (this path is for ordinary background Bash tasks; a `Monitor` call is denied by the adapter and runs as a daemon-owned watch — see Runtime Notes). A `BackgroundTaskDoneEvent` must start a REAL turn — `agent.py:_idle_notifier_for` re-injects it with `channel.push_back(..., is_internal=True)` so `main_loop` runs a follow-up the model can actually act on. A notification card alone is a dead end: the model never sees it, so the card is never followed by anything. Guard against runaway loops with the daemon-scoped `IdleTurnBudget` (`MAX_IDLE_AUTO_TURNS`, reset by any real user message) — an instant-firing `Monitor` notifies the moment its turn ends, and its own follow-up turn can spawn another. `BackgroundTurnDoneEvent` is the exception: the CLI already ran that turn, so it only needs its card. **That path only works if the task is still ALIVE at turn end.** `claude_turn._promote_pending_to_stale` and `_stop_tasks` are deliberately two different things: promotion is the SDK #788 guard (a late notification must not contaminate a later turn) and applies to *every* turn, while stopping is orphan cleanup and applies only to ABANDONED turns (transient/non-retryable API error). **A Monitor id must never be promoted.** A watch is armed precisely to outlive its turn and report back many times, so "a notification for an id from an earlier turn" is its normal operation, not a #788 leak. Promoting it made the watch's own report raise `StaleLeakError` → reconnect → the CLI's children (every live watch) died, so a `while [ ! -f *.exit ]` watch that finished mid-turn silently killed itself and took the user's in-flight answer with it (2026-11-06, oc_9540cd47…). `_single_turn` collects Monitor ids into `watch_tasks` (recovered from the tool_use block, since `task_type` cannot tell a Monitor from a plain `local_bash`) and `_promote_pending_to_stale(..., watches)` excludes them from `stale_tasks` while still RETURNING them — an abandoned turn must still stop a watch it orphaned. Ordinary background commands keep the #788 protection. Pinned by `test_a_monitor_is_never_promoted_to_stale` + `test_control_promoting_a_monitor_makes_its_own_report_fatal`. A completed turn's tasks must never be stopped — the CLI reports the reaping itself as `status=stopped` ~1s after the turn and that becomes the only notification the drainer can ever surface, silently killing the feature (2026-09-28). `test_stop_task_has_exactly_one_call_site` (AST) pins `stop_task` to that single call site. **The drainer must be restartable, not merely armable.** Every client replacement cancels and replaces the task — `SDKThread.reconnect()` calls `_rearm_idle_drain()` (which is `start_idle_drain(..., restart=True)`) because a task parked on a receive future from the closed client is `not done()` and the lazy path will never replace it. The re-arm lives THERE, not in `ClaudeCodingAgent.reset`: `reset()` only covers user reconnects (`/clear`, `/model`, `/effort`, `/agent`), while the watchdog stall recovery and the stale-leak recovery reconnect from inside `run_turn_with_reconnect` and never reach `reset()` — after the first such reconnect the daemon read nothing between turns until it was restarted (2026-11-03, oc_956058b1…: a Monitor fired every minute for three turns, the CLI answered all three, and its card never updated; the rotated log's last `SDK client connected` predated the watch and no idle event followed it). `start_idle_drain._arm` ALSO treats "the client changed under the task" (`_drain_client_is_stale`) as an implicit restart, so an arm call that forgets `restart=True` still heals it; and `_idle_drain_loop` wraps its whole body so an escaping exception logs and reopens the stream instead of killing the task. A dead drain task is invisible — we hold a strong reference, so CPython never prints "Task exception was never retrieved", and the daemon looks healthy while every between-turn event queues unread (2026-10-28: a group's Monitor fired every 15 minutes for hours, not one card reached Lark, and the piled-up stale notifications then forced reconnects that killed the Monitor subprocess).
- `/fork` (read-only, multi-turn sub-thread) is exposed via `CodingAgent.supports_fork()` / `fork()` and orchestrated by `nemo/fork.py`'s `ForkManager` (one read-only sub-agent + SDK subprocess per fork, routed by Lark `thread_id`). Supported on **Claude** (resume + `fork_session=True`, branching the transcript; read-only via bash sandbox with a scratch cwd so the project sits outside the writable workspace) and **Codex** (copy the parent rollout jsonl to a new thread id then resume the copy — Codex resume *appends*, so the fork needs a private copy; read-only via native `sandboxMode=read-only`, so cwd can stay the project). OpenCode is unsupported. Both keep full parent context but cannot modify project files.

## Runtime Notes

- Dev install:
  ```bash
  pip install -e .
  nemo --chat-id <ID> --project-dir <DIR>
  ```
- Do not use `pipx install captain-nemo` on the dev machine. `pipx` is only for end-user installs.
- Profile config lives in `~/.nemo/<profile>.json`.
- Relay config can come from config or `NEMO_RELAY_URL` / `NEMO_RELAY_API_KEY`.
- Claude CLI selection: claude-agent-sdk's `_find_cli` returns its own bundled binary before it ever looks at PATH, so a stale bundle can shadow a newer installed `claude`. `nemo/claude_agent.py:_resolve_cli_path` version-compares bundled vs PATH vs `~/.local/bin` and pins the newest via `ClaudeAgentOptions(cli_path=…)` — a CLI older than the running model mis-names it (self-reports the wrong Opus generation, and fills the git `Co-Authored-By` trailer from its stale model table). Every options builder must pass `cli_path`.
- **Web search is client-side (`nemo-search`).** `WebSearch` is Anthropic's *server* tool (`web_search_20250305` / `web_search_20260209`) — the search runs on the API backend, and a gateway that speaks the Anthropic wire protocol without implementing it does not error: it returns FABRICATED results (2026-11-08, opencode.ai/zen/go: one query came back as the tool call echoed verbatim, another as a submodel's prose "I don't have a web search tool available here"). Both are shaped exactly like real results, so nothing downstream can tell. `ClaudeCodingAgent._on_websearch_call` denies `WebSearch` whenever the effective `ANTHROPIC_BASE_URL` is not Anthropic's and names the replacement; `nemo/search.py` + the `nemo-search` console script talk to a search API from the daemon itself (Brave default, `ddg` / `searxng` alternatives), so search works on every model. Config lives in `~/.nemo/search.json` (`{env:VAR}` supported); `NEMO_SEARCH_BACKEND` overrides the backend. Not yet wired for the `claude-cli` adapter, which has no PreToolUse hook.
- **No self-scheduled turns.** Claude Code's `CronCreate` / `CronList` / `CronDelete` / `ScheduleWakeup` are REPL-only: their scheduler fires only while the interactive REPL is idle, and Nemo drives the CLI headless through the Agent SDK. They register a job, return success, and never tick — a real incident promised a group 15-minute progress reports that never came (2026-10-27). They are denied in every Claude session via `_CRON_DISALLOWED_TOOLS` in `nemo/claude_agent.py`, and the agent prompt says so. Never re-allow them or remove the deny. Recurring work is a watch (next bullet), whose ending the daemon turns into one real follow-up turn.
- **A watch (the `Monitor` tool) is a DAEMON-OWNED process — `nemo/watches.py`.** The model still calls `Monitor` with `command` / `description` / `timeout_ms`; `ClaudeCodingAgent._on_pre_tool_use` DENIES that call and hands its input to `WatchManager.arm()` on the host loop (wired by `set_watch_armer` in `main_loop`). Nemo spawns the command itself (`asyncio.create_subprocess_shell`, `start_new_session=True`, cwd = project dir), appends every stdout line to its one 👀 card, and treats process exit as the end. **Identity is the spawn and lifecycle is process exit: nothing is reconstructed from CLI internals.** That is the whole point — every previous Monitor bug (report attribution via a transcript byte cursor, stale-leak promotion killing the CLI's children, a between-turn fire the drainer missed, reconnects killing watches) was a disagreement between the daemon's guess and the CLI's behaviour. Do not reintroduce any of that machinery; the module docstring has the post-mortem.
  - **The deny reason is the model's receipt.** It names the watch id, says the process is independent of the CLI and survives `/clear`/reconnects, says output lands on the card so the model must NOT relay poll output, and gives the stop command. A silent success would leave the model believing it still owns a CLI task.
  - **One watch owns ONE card, for its whole life.** `_start_watch_card` posts the marker (`_post_monitor_marker`, label `watch`, and `db.record_monitor`); every output line is one report appended via `_deliver_idle_card` → `MonitorCards` keyed by watch id; `_close_monitor_card` freezes it with a grey header and an end label (`completed` / `failed` / `stopped` / `timeout`); rollover past `TURN_CARD_ROLLOVER_BYTE_LIMIT` continues on a new part instead of dropping what the user was shown. There is deliberately no generic fallback card — an unattributable report is a bug and must post a red error card.
  - **Cadence is honest by construction.** `Monitor` has no interval field; the rhythm is the `sleep` inside the command, so the prompt states `ONE POLL = ONE REPORT` (emit a line every iteration, set that `sleep` to the promised interval, never gate the echo behind a counter) and the card footer reports the LAST `sleep` plus `timeout_ms` (`cards.monitor_cadence`). Since every stdout line becomes a report, the footer cannot drift from reality.
  - **Bounded and stoppable.** `MAX_LIVE_WATCHES = 3` is enforced in `WatchManager.arm` (the refusal names the escape hatch: `.stop`, or fold several watches into one command). Stop = `touch ~/.nemo/watches/<watch_id>.stop`, polled once a second by `_guard`, which also enforces `timeout_ms`. Termination is `SIGTERM` to the process group, then `SIGKILL` after `KILL_GRACE_SECONDS`. A non-`stopped` ending pushes ONE wake-up turn (`_watch_done_message`, tail of output) so the model can answer; a `stopped` watch stays silent because the user asked for it.
  - **Reconnects do not kill watches.** `/clear`, `/model`, `/effort` and stale-leak recovery replace the SDK client, not the daemon's processes; `_restart_client` only clears the monitor registry when `_watch_manager.live_ids()` is empty. A daemon restart does kill them (they are our children), so `armed_monitors` rows are surfaced once as a restart notice on the next turn and the default is explicitly **do not re-arm** — only the user asking again should re-arm.

## Architecture

- `nemo/channel.py`: abstract user/channel boundary
- `nemo/coding_agent.py`: abstract coding-agent boundary
- `nemo/agent_factory.py`: agent kind → `CodingAgent` adapter, agent/model compatibility
- `nemo/lark_channel.py`: Lark-backed channel implementation
- `nemo/claude_agent.py`: Claude Agent SDK adapter (in-process Python SDK via `SDKThread`)
- `nemo/codex_agent.py`: Codex adapter that spawns the node sidecar per turn
- `codex_sidecar/run_turn.mjs`: node sidecar around `@openai/codex-sdk` — streams JSON events on stdout, reads prompt from stdin. Requires `node` and the `codex` CLI on `PATH`.
- `nemo/turn.py`: typed turn events and streaming turn runner
- `nemo/relay_events.py`: relay WebSocket / poll event source
- `nemo/lark/`: Lark API/auth/direct-event plumbing

## Lark Constraints

- Lark 长连接 is single-consumer per app. Prefer the relay server for real usage.
- Card V2 constraints matter here:
  - no `action` wrapper
  - no `note` tag
  - `collapsible_panel` headers must use `plain_text`
- `get_message` loses original card body content. Persistent config/state must not depend on reading interactive card bodies back.
- `<font color=…>…</font>` (and any inline HTML) cannot span a markdown paragraph break (`\n\n`): the open lands in one block, the close in the next, and Lark leaks a bare `</font>` into the rendered card. Keep a grey `_note_element` to a single line; render multi-line content as plain markdown. A literal `<name>`-style token in card text also opens a stray tag — write `NAME`, not `<name>`.
- Form submit (`form_action_type: "submit"`): Lark puts every *named* form child into `action.form_value` and may DROP the button's `action.value`. So (a) leave the submit button nameless or the single-field `form_value` becomes multi-field and the relay JSON-encodes it (breaking a `startswith(prefix)` route), and (b) the relay must fall back to `event.context.open_chat_id` / `open_message_id` for routing since `value.chat_id` can be missing. Encode the routing discriminator in the *select option value* (e.g. `model_switch:<name>`), not in the button.

## Debugging

- Pulling a chat's messages when analysing a bug — three sources, most-useful first:
  - **Daemon log (primary / forensic).** Map the chat to its daemon, then read the log:
    ```bash
    pid=$(cat ~/.nemo/pids/<chat_id>.pid)
    less ~/.nemo/logs/nemo-$pid.log
    ```
    Every inbound event is logged as `Event: type=… chat=… sender=… text=…` and every reply as `Response sent …`. This is the source of truth for what the daemon actually saw and did (including synthesised internal messages and card actions).
  - **Lark itself (the real conversation).** Use `lark-cli` (lark-im skill) to read what users actually sent, including interactive card bodies that `get_message` strips: `lark-cli im +chat-search` (find chat_id by group name), `+chat-messages-list --chat-id <cid>` (history, time range / pagination), `+messages-search` (keyword / sender / time), `+messages-mget` (batch by `om_` ids). Why lark-cli and not nemo's own code: `nemo/lark/api.py` only wraps the runtime primitives the daemon needs — single-message `get_message` (which also drops card bodies), plus send / update / download / members. It has **no** history-list (`GET /im/v1/messages?container_id=…`) or message-search wrapper, and Lark message *search* is user-identity-only (the daemon's bot token can't do it). lark-cli already wraps list + search across both identities, so it's the pragmatic forensic tool rather than adding a runtime-unused wrapper to nemo.
  - **Relay queue (live only).** `GET <relay_url>/replies/chat:<chat_id>?since=` (header `Authorization: Bearer <relay_api_key>`) returns only UN-consumed messages — an active daemon has already drained them, so this reflects the live queue / injected test events, not history.

## Error Handling

- Never `except Exception: pass` — always log the exception. Silent swallowing hides bugs (e.g. the zombie CLI subprocess bug was invisible because `__aexit__` failures were silently passed).

## Typing Rule

- Do not introduce `Any` in repo Python code.
- For opaque runtime handles, use `object` or a narrow `Protocol`.
- For SDK/channel boundaries, define the minimal protocol the caller actually needs.
- For JSON-like payloads, use shared aliases from `nemo/types.py` instead of `dict[str, Any]`.

## Validation

- Bug fixes must include a test case that covers the fix — and that test must be shown to FAIL without the fix. A regression test that passes with the bug present is worse than no test: it reports "covered". Make the control PERMANENT (`test_control_*`, patching the fix out with `mock.patch.object`) rather than an in-place source A/B that you revert — a pyc can hide a same-size same-second edit, and a reverted control protects nothing afterwards. See `test_control_cumulative_expectation_hangs_the_turn`.
- Two e2e-harness rules, both learned from a run that wasted an afternoon chasing a phantom daemon crash:
  - **Never `stdout/stderr=subprocess.PIPE` a long-lived child you don't drain.** Spawn through `scripts/e2e_test.py:spawn_logged`, which puts stderr on a file. A PIPE plus a single `readline()` (what `start_nemo` used to do) deadlocks any child that writes more than the 64KB kernel buffer — it looks EXACTLY like a daemon deadlock (silent log, no heartbeat) and also eats the traceback when the daemon really does die. `test_e2e_never_pipes_an_undrained_stream` (AST guard) and `test_spawn_logged_survives_a_stderr_flood` (behavioural) pin it.
  - **Identify an artifact structurally, never by wall-clock timestamp.** Lark stamps cards with second-resolution `create_time`, and back-to-back turns routinely land in the SAME second. Use `done_cards(chat_id, after=...)` and count (card #1 = first turn, #2 = follow-up) instead of `wait_for_response(after=<timestamp>)` whenever a phase must tell two turns' cards apart. And remember a turn's Done card is not necessarily the NEWEST bot message — marker / idle-notification cards land on top of it — so `wait_for_response(require_done=True)` scans the recent window (`newest_completed_msg`) rather than reading only the latest one (2026-10-29: the 👀 marker card made ID01 report "no Done card" for turns that had completed).
- Minimum regression pass after core changes:
  ```bash
  pytest tests/test_main.py tests/test_interfaces.py tests/test_permissions.py tests/test_turn.py -q
  ```
- Run relay-injection e2e when touching channel/event/permission flow:
  ```bash
  python3 -u scripts/e2e_test.py --skip-sdk
  python3 -u scripts/e2e_test.py --perm
  ```
  The e2e injects events via the relay and uses the bot/tenant token (app_id +
  app_secret) to send/read cards — it does NOT need a Lark **user** token. An
  "User token expired / refresh failed" line is expected and auto-falls back to
  relay; never stop to refresh it. Run with `-u` (stdout is block-buffered when
  piped — without it the run looks frozen until exit; don't kill it, SDK phases
  take minutes). See the `scripts/e2e_test.py` header for full details.
- **The e2e picks its own model.** The daemon's compiled-in default
  (`claude-opus-5`) is only routable against Anthropic; on a host whose
  `ANTHROPIC_BASE_URL` points at a gateway (this machine: opencode zen/go) every
  SDK turn dies with `400 Model is unavailable` before any nemo code runs.
  `scripts/e2e_test.py` therefore defaults to `oc-deepseek-v4.1-flash` for
  claude/codex/opencode (skipped for claude-cli, whose preset allowlist does not
  include it). Override per run with `--model`, or globally with
  `NEMO_E2E_MODEL`. Do not "fix" a failing case by dropping `--model`.
- **Lark will not hand an interactive card's body back.** `get_message` / the message-list API returns a title plus a placeholder image for Card V2, so an e2e cannot assert what a card *says* — only its title and its message id. Phase `--monitor` therefore proves card merging structurally (same message id, monotonic report counts from the daemon's `Monitor card appended … (N reports)` lines) and leaves per-section content to the unit tests. Set `NEMO_E2E_KEEP_CHAT=1` to keep the phase's temp group so the cards can be inspected by eye.
- Interactive card features (forms / dropdowns / buttons) must be tested at all three layers, not just the daemon. A daemon test that hand-builds `action_value={"action": …}` stubs away the wire format and will miss bugs in how Lark/the relay actually deliver the action (this is exactly how a `/model` picker form submit shipped broken — the relay dropped it because `value.chat_id` was empty). Cover:
  - `relay/test_relay.py` — POST a realistic webhook (try with AND without `action.value`, since Lark V2 form submits are flaky about preserving it).
  - `tests/test_relay_events.py` — round-trip the relay reply dict through `_relay_msg_to_event`.
  - `tests/test_agent.py` — the daemon main-loop handler.
  - `python3 scripts/e2e_test.py --picker` for the live `/model` picker chain.
  - `python3 scripts/e2e_test.py --recall-picker` for the `/session recall` picker. NB: the relay's `BOT_OWNED_CARD_PREFIXES` "Selected:"-flash suppression only takes effect once the **remote** relay (`/opt/nemo-relay/relay.py` on the configured `relay_url` host) is redeployed — repo `relay.py` is verified by `relay/test_relay.py`, but the live host can lag (same caveat as `--fork`). A stale remote relay shows as a SKIP, not a failure.
- `/fork` (read-only sub-thread) is thread-routed, so it has the same wire-format risk as the picker — the relay must forward `thread_id` or follow-ups never reach the fork. `python3 scripts/e2e_test.py --fork` covers the live round-trip; because the configured remote relay predates the `thread_id` forwarding fix, this phase spins up a LOCAL relay (repo `relay/relay.py`) for inbound events while outbound card sends still hit real Lark. The `/fork` message must anchor on a REAL Lark message id (Lark rejects reply-in-thread to a fabricated id); the phase reuses the daemon's start-card id. No user token needed — relay injection + the tenant token suffice.
